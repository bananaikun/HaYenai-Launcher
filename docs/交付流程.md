# HaYenai 启动器 · 交付流程

> 五阶段流水线。每阶段有入口条件、动作、落盘产出物、可判真假的出口判据。
> 判据不过就不进下一阶段，没有「先做着再说」。

---

## 流水线总览

```
需求确认 → 画布评审 → 实现 → 验证 → 发布
   │           │         │       │       │
 需求卡      画布+标注   分支+自测  验证报告  tag+CHANGELOG+产物
```

| 阶段 | 一句话 | 典型耗时 |
|---|---|---|
| 1 需求确认 | 把「我想要」变成「怎么算做完了」 | 10 分钟 |
| 2 画布评审 | 先看结构，再写代码 | 1–2 轮 |
| 3 实现 | 一个分支只解决一张需求卡 | 按需求 |
| 4 验证 | 用判据证明它能跑，不是「看起来能跑」 | 30 分钟 |
| 5 发布 | 版本、记录、合规包一起出 | 20 分钟 |

---

## 阶段 1：需求确认

### 入口
脑子里有个想法，或者发现了问题。

### 动作

写一张需求卡，**不超过一屏**。写不满说明没想清；写超了说明该拆。

### 产出物

`docs/requirements/<YYYY-MM-DD>-<slug>.md`：

```markdown
# 首页启动卡改单列

## 目标
账号卡从右侧栏移到启动卡下方，主区不再左右分栏。

## 非目标
不动版本页、不动设置页。

## 验收判据
- 窗口宽 900px 时首页无横向滚动条
- 账号卡与启动卡垂直间距 16px
- 深色主题下卡片对比度不下降

## 涉及界面
首页（HomeView）、账号卡组件

## 上游基线
27b1488
```

### 出口判据
- [ ] 「验收判据」每条都能被机械判定（能写测试或能截图对比）
- [ ] 「非目标」非空（说不清不做什么，就一定会扩散）
- [ ] 记录了当前上游基线 commit

---

## 阶段 2：画布评审

### 入口
需求卡通过。

### 动作（顺序不能换）

1. **先出画布**，不写代码。用 WorkBuddy 内置画布出 HTML/SVG 稿（或沿用上游现有界面截图做标注版）
2. 停下等标注，不许自己替主人做决定
3. 收到标注后**增量改**，不推倒重来
4. 明确收到「确认」二字，才算过闸

### 产出物

`docs/canvas/<slug>/`
- `v1.html`（或导出的 png）
- `notes.md`：每轮标注 → 处理结果

`notes.md` 模板：

```markdown
## 第 1 轮（10-17）
| # | 标注 | 处理 | 状态 |
|---|---|---|---|
| 1 | 启动按钮太靠右 | 改为卡片右下、留 24px | 已改 |
| 2 | 账号头像太大 | 54 → 44 | 已改 |

## 确认
- 确认时间：—
- 确认人：主人
```

### 出口判据
- [ ] 每一轮标注都有「处理」和「状态」，没有悬空项
- [ ] 主人明确说过「确认」
- [ ] 画布与需求卡的验收判据逐条对得上

---

## 阶段 3：实现

### 入口
画布已确认。

### 动作

```bash
git switch -c feat/<slug> main
```

- 按需求卡范围改，**只改该改的包**
- 每完成一个可独立工作的原子，就先跑局部检查（`vue-tsc --noEmit` / `cargo check`）
- 中途发现设计不对 → 回阶段 2，不要边写边改设计
- 发现上游代码有坑 → 记进 `docs/canvas/<slug>/notes.md` 的「踩坑」小节，不在本需求里顺手修

### 产出物
- 工作分支（≤ 3 天）
- 提交（符合 `协作规范.md` §3）

### 出口判据
- [ ] 完整自测清单全绿（`协作规范.md` §6.2）
- [ ] `git diff main...HEAD --stat` 里没有无关文件
- [ ] 自审检查表 10 条全勾

---

## 阶段 4：验证

### 入口
分支自测通过。

### 动作

真构建一次，不许用 dev 模式替代：

```bash
pnpm app:build
```

产物位置：

| 产物 | 路径 |
|---|---|
| 前端 | `apps/app-frontend/dist/` |
| 二进制 | `apps/app/target/release/` |
| 安装包 | `apps/app/target/release/bundle/`（NSIS / msi / dmg / AppImage 取决平台） |

冒烟清单（每次构建后逐条过）：

- [ ] 双击能打开，窗口在 5 秒内可见（不是白屏）
- [ ] 首次启动能进首页，侧栏导航点击都能切页
- [ ] 设置页能打开、能改一项并保存
- [ ] 版本列表能加载（网络正常时）
- [ ] 关闭后进程真的退出（任务管理器无残留）
- [ ] 二次启动不报占用错误（单实例/数据目录锁）

资源占用按 `协作规范.md` §7 口径测一次，填进验证报告。

### 产出物

`docs/releases/v<X.Y.Z>-verify.md`：

```markdown
# v0.2.0 验证报告

## 构建
- 构建时间：—
- 产物：`apps/app/target/release/bundle/nsis/HaYenai_0.2.0_x64-setup.exe`
- 体积：—

## 冒烟
| 项 | 结果 | 备注 |
|---|---|---|
| 打开 | ✅ | 3.2s 可见 |
| 导航 | ✅ | |
| 设置保存 | ✅ | |

## 资源占用（三次冷启动）
| 次 | 常驻内存 | 启动耗时 |
|---|---|---|
| 1 | — | — |
| 2 | — | — |
| 3 | — | — |
| 中位数 | — | — |

## 回归对照
- [ ] 上游原有功能未被破坏：版本安装 / 实例启动 / 账户登录

## 结论
通过 / 不通过（不通过则列出阻断项）
```

### 出口判据
- [ ] 冒烟清单 6 条全过
- [ ] 资源数据有 3 次实测，不是估计
- [ ] 回归对照确认上游功能未破坏
- [ ] 严重问题数 = 0（有严重问题就退回阶段 3）

## 阶段 5：发布

### 入口
验证报告结论为「通过」。

### 动作

```bash
# 1) 版本号（唯一来源）
#    改 apps/app-frontend/package.json 的 version
# 2) 变更记录
#    从 git log <上个tag>..HEAD 提炼进 CHANGELOG.md
# 3) 提交 + 打 tag
git commit -am "chore(release): v0.2.0"
git tag hayenai-v0.2.0
# 4) 重新构建（版本号变了必须重建）
pnpm app:build
```

### 产出物

- 带 tag 的 `main`
- `CHANGELOG.md` 新条目
- 安装包 + 校验值：

```bash
sha256sum <安装包> > <安装包>.sha256
```

- 合规包（对外分发时必须一起给）：
  - [ ] 对应 tag 的源码（GitHub Release 的 source zip 即可）
  - [ ] `COPYING.md` 与各包许可文件未删改
  - [ ] README / 关于页保留「基于 Axolotl（GPL-3.0-only）」归属
  - [ ] 未重新引入 Modrinth 商标与受限素材

### 出口判据
- [ ] tag 指向的提交能干净构建（不在脏工作区打 tag）
- [ ] 安装包 sha256 与发给别人的一致
- [ ] CHANGELOG 条目能让用户判断「要不要升」
- [ ] 回滚路径已在发布说明里写明

## 阶段闸门总表

| 闸门 | 放行判据（一句话） | 不过怎么办 |
|---|---|---|
| 1→2 | 验收判据可机械判定 | 回去重写需求卡 |
| 2→3 | 主人明确说「确认」 | 继续改画布 |
| 3→4 | 自测清单全绿 + diff 无无关文件 | 修完重跑 |
| 4→5 | 冒烟 6 条全过 + 资源实测 + 无严重问题 | 退回实现 |
| 5→发布 | tag 干净 + sha256 已记录 + 合规包齐 | 不许发 |

## 异常与回退

### A. 画布被推翻
最多重出 1 版。第二版仍被推翻 → 回阶段 1 重新确认需求，说明是需求没想清，不是画得不好。

### B. 构建挂
按顺序排查：

1. 子模块在不在（`git submodule status` 无 `-` 前缀）
2. pnpm 版本是不是 10.33.2（`corepack pnpm@10.33.2 -v`）
3. `pnpm install` 是否完整（`packages/api-client/dist` 存在）
4. Rust 工具链是否 1.95.0（`rustc --version`）
5. 以上都对 → 清 `apps/app/target` 重编，慢但可靠

### C. 上游 breaking 改动
1. 先 `git stash` 自己的分支
2. 在干净 `main` 上同步上游，确认上游自身能构建
3. 再合并自己的分支，冲突时保上游语义
4. 若上游把你要改的模块整个重构了 → 暂停需求，重新评估画布

### D. 发版后发现严重 bug
1. 立刻在 `CHANGELOG.md` 顶部加 `### 撤回`，写明影响版本与规避方式
2. 从上一个可用 tag 打 `fix/<slug>` 分支修
3. 修不好就回滚发布：重新发布上一个 tag 的产物，并把新版本标记为 pre-release
4. **不删 tag**，不覆盖已发布的二进制（用户已经下过了）

### E. 数据目录标识变更（改 identifier 时必看）
`identifier` 决定用户数据目录（Windows 为 `%APPDATA%\<identifier>`）。改它等于换数据目录：
- 必须先写迁移逻辑（旧目录 → 新目录）
- 迁移前先备份，迁移后校验文件数
- 没有迁移逻辑就不许改 identifier

## 度量与复盘

每次发布只记三件事，多记没人看：

| 指标 | 来源 |
|---|---|
| 常驻内存中位数 | 验证报告 |
| 冷启动到窗口可见 | 验证报告 |
| 本次踩坑数（以及其中几个是重复踩的） | 需求卡/notes.md |

复盘只看一个问题：**这次有没有踩到以前踩过的坑？** 有，就把那条写进 `协作规范.md` 的对应章节，别再靠记忆。
