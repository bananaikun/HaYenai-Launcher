# HaYenai 启动器 · 协作规范

> 适用对象：项目唯一维护者。所有条款按「一个人 + 一个键盘」设计，不依赖第二个人。
> 每条尽量给命令、模板或判据；只讲原则的条目已删。

---

## 1. 仓库与目录约定

### 1.1 这是 monorepo，不是单体

```
apps/
├── app/                 Rust + Tauri 2 桌面端（含 src-tauri 逻辑、capabilities、icons）
├── app-frontend/        Vue 3 + Vite 界面（真正被 tauri 打进去的前端）
├── installer-ui/        安装器界面
├── telemetry-dashboard/ Nuxt 面板
├── telemetry-worker/    遥测 Worker
└── website/             官网（Nuxt）
packages/
├── ui/ assets/ api-client/ app-lib/ daedalus/ ariadne/ …
└── tooling-config/      共享 lint/ts 配置
```

**改界面的落点只有 `apps/app-frontend/`**；改窗口、进程、启动逻辑落 `apps/app/`；改公共组件落 `packages/ui/`。改错层会出现「改了没生效」——因为 tauri 打的是 `apps/app-frontend/dist`。

### 1.2 不许入库的东西

- `node_modules/`、`dist/`、`.nuxt/`、`target/`、`apps/app/src-tauri/target/`
- 本地环境文件（`.env`、`.env.local`）、签名私钥（`*.key`、`*.pem`）
- 构建日志、临时截图、调试 dump

判断标准：**这个文件能不能由 `pnpm install` + 一条构建命令重新生成？** 能，就不提交。

### 1.3 子模块

两个子模块是构建依赖，不是装饰：

```bash
git submodule update --init --depth 1
git submodule status   # 两个都要有 commit，不能是 - 开头
```

改动子模块内容视为改上游代码，必须单独提交并说明原因。

## 2. 分支策略（trunk-based + 上游同步）

### 2.1 分支模型

单人维护用 trunk-based，不搞 develop/release 分支矩阵。

| 分支 | 用途 | 寿命 |
|---|---|---|
| `main` | 恒可构建、恒可跑 | 永久 |
| `feat/<slug>` | 单个功能 | ≤ 3 天 |
| `fix/<slug>` | 单个缺陷 | ≤ 3 天 |
| `chore/<slug>` | 工程杂务（依赖、脚本、配置） | ≤ 1 天 |
| `exp/<slug>` | 试验，允许脏 | 1 周内必须出结论（合入或删除） |

超过 3 天的工作分支必须拆小，或者承认它其实是 `exp/`。

### 2.2 上游同步（这个项目最重要的一条纪律）

```bash
git remote -v                      # upstream 必须指向 Mystic-Stars/Axolotl
git fetch upstream
git switch main
git merge upstream/main            # 冲突优先保上游语义，本地改动让路
```

规则：

- 同步前先记基线：`git rev-parse HEAD`，写进当天的需求卡
- 同步后必须跑 §6 的完整自测清单，不许「只是合并，应该没事」
- 一次同步只解决冲突，不在同一个提交里夹带功能改动
- 上游大改（`apps/app-frontend` 结构变动）时，先停下评估自己的改动还值不值得保留

### 2.3 合并方式

工作分支收尾用 squash 合入 `main`，保持 `main` 一条线：

```bash
git switch main
git merge --squash feat/xxx
git commit                       # 提交信息按 §3 写
git branch -d feat/xxx
```

不要 `merge --no-ff` 造一堆无意义的合并节点。

## 3. 提交信息规范（Conventional Commits 中文版）

### 3.1 格式

```
<type>(<scope>): <一句话说清改了什么>

<为什么改 / 影响面 / 注意事项>
```

标题不超过 50 字，句末不加句号。正文只在「看标题猜不到」时写。

### 3.2 type 取值

| type | 用于 |
|---|---|
| `feat` | 新功能、新界面元素 |
| `fix` | 修缺陷 |
| `perf` | 纯性能改动（资源占用、启动耗时） |
| `refactor` | 不改变行为的结构调整 |
| `style` | 只改外观/格式（换皮、排版、主题） |
| `build` | 构建脚本、打包配置、依赖版本 |
| `docs` | 文档 |
| `chore` | 杂务（版本号、CI、清理） |
| `revert` | 回滚，正文写被回滚的提交 hash |

### 3.3 scope 建议

`ui`（app-frontend）、`app`（Tauri 侧）、`pkg-ui`（packages/ui）、`deps`、`build`、`docs`、`brand`、`i18n`。

### 3.4 正例 / 反例

```
feat(ui): 首页启动卡改用单列布局，账号卡下移

fix(app): 启动器在 WebView2 目录被占用时给出明确提示，不再静默退出

style(brand): 换用液态玻璃配色令牌，控件位置不动

build(deps): pnpm 固定 10.33.2，避免嵌套调用 pnpm 报 ERR_PNPM_BAD_PM_VERSION
```

反例（会被打回）：

```
update            ← 改了什么？不知道
fix bug           ← 哪个 bug？
.                 ← 无信息
一堆改动            ← 拆开
```

### 3.5 一个提交只做一件事

判据：**能不能用一句「读者能看懂的话」说清？** 说不清就是该拆。

## 4. 版本与变更记录

### 4.1 版本号

沿用上游的 SemVer 节奏，但**标签加自己的前缀**避免与上游 tag 撞车：

```bash
git tag hayenai-v0.1.0
```

- 上游是 `v1.10.0-beta.1` 这种，本地 tag 用 `hayenai-v*`，一眼能分清来源
- 0.x 阶段：破坏性变更也走 MINOR，别急着跳 1.0
- 版本号来源是 `apps/app-frontend/package.json`（`tauri.conf.json` 的 version 指向它），改版本只改这一处

### 4.2 CHANGELOG

`CHANGELOG.md` 用 Keep a Changelog 结构：

```markdown
## [0.2.0] - 2026-11-01
### Added
- 首页支持自定义背景图轮播
### Changed
- 侧栏导航图标换成线性风格
### Fixed
- 实例目录含中文时下载卡在 0%
### Removed
- 移除了上游的 xx 面板（原因：……）
```

规则：

- 发版时从 `git log <上个tag>..HEAD` 提炼，不许写「若干优化」「体验提升」
- 每条都要能让用户判断「这跟我有没有关系」
- 破坏性变更单独一节 `### Breaking`，写清怎么迁移

### 4.3 上游版本关系

在 `CHANGELOG.md` 顶部维护一行基线：

```
上游基线：Mystic-Stars/Axolotl @ 27b1488（1.10.0-beta.1）
```

发版前对一次：上游若已前进很多，先决定是否同步再发。

## 5. 依赖与开源合规

### 5.1 许可事实（不可协商）

| 项 | 事实 |
|---|---|
| 桌面包主许可 | **GPL-3.0-only**（注意：不是 "or later"） |
| 其他包 | 各自声明，见包内 `COPYING.md` / `LICENSE` |
| 商标限制 | Modrinth 商标、logo、封面图**不得**随改版重新引入（`COPYING.md` 明文） |
| 分发义务 | 对外发二进制 ⇒ 必须同时提供对应源码，且保留许可与版权声明 |

推论（照做，别辩论）：

1. 本项目若对外发版，**必须开源**，且不能改成别的许可
2. `GPL-3.0-only` 不能与 `GPL-2.0-only` 代码混用；`Apache-2.0` / `MIT` / `BSD` / `ISC` 可以
3. 不许引入 `SSPL`、`BUSL`、`Commons Clause`、任何「禁止商用/禁止再分发」的依赖
4. 品牌替换 ≠ 抹除来源：README / 关于页必须保留「基于 Axolotl（GPL-3.0-only）」与 Modrinth 的归属说明

### 5.2 新增依赖四问

按顺序问，任何一问过不去就不加：

1. **标准库/现有依赖能做吗？**（monorepo 里 11 个包，先翻 `packages/`）
2. **体积代价多大？** 前端包看 gzip 后体积，Rust 看编译时间与二进制增量
3. **许可证兼容吗？** 对照 §5.1
4. **它还在维护吗？** 一年无提交、issue 无人回的包不加

### 5.3 依赖操作规范

```bash
pnpm add <pkg> --filter @modrinth/app-frontend   # 只装到需要的包
pnpm remove <pkg> --filter <包名>
pnpm install                                     # 装完必须让 lockfile 一起提交
git diff pnpm-lock.yaml | head -40               # 确认没有意外的大面积升级
```

⛔ 不要手动编辑 `pnpm-lock.yaml`；⛔ 不要为了装一个包去改 `packageManager` 字段。

### 5.4 来源标注（发版前逐条核对）

- [ ] `README.md` 写明「基于 HaYenai（GPL-3.0-only）」并给出仓库链接
- [ ] 保留上游 `COPYING.md` 与各包许可文件，未删改
- [ ] 关于页/第三方声明页可见上游与 Modrinth 的归属
- [ ] 新引入的第三方资源（图标、字体、音效）在 `THIRD_PARTY_NOTICES` 或包级声明里登记
- [ ] 未重新引入 Modrinth 商标与受限素材

## 6. 代码评审与自测

单人项目没有 PR 评审，用三层替代。

### 6.1 写码前：一句话意图

开工前在需求卡里写清：

```
意图：把首页启动卡从两列改为单列，账号卡下移
判据：窗口宽 900px 时无横向滚动；账号卡在启动卡下方 16px 处
```

写不出判据 = 需求没想清，先别写码。

### 6.2 提交前：固定自测清单

按顺序跑，任何一步红就停下：

```bash
# 0) 环境（本机必需）
export PATH="/tmp/pnpm-bin:/c/Program Files/nodejs:/c/Users/banan/.cargo/bin:$PATH"
corepack pnpm@10.33.2 -v        # 必须是 10.33.2

# 1) 只跑改动涉及的包（快）
pnpm --filter @modrinth/app-frontend exec vue-tsc --noEmit
pnpm --filter @modrinth/app-frontend lint

# 2) Rust 侧（改过 apps/app 才需要）
cd apps/app && cargo check && cargo clippy --all-targets

# 3) 全套（发版或动公共包时）
pnpm lint
pnpm test

# 4) 真构建（改过前端结构/打包配置时）
pnpm app:build
```

### 6.3 冷置自审

提交前至少隔一晚再看 diff：

```bash
git diff main...HEAD --stat
git diff main...HEAD
```

只看 diff，不看记忆。重点找三类东西：

- 顺手改的无关代码（违背最小改动）
- 自己新造的孤儿（没用的 import / 变量 / 样式类）
- 需要但没写的注释（为什么这么绕）

### 6.4 强制外部复审的触发条件

出现以下任一情况，**禁止只靠自审发布**，必须找人（或另起一轮独立 review）过一遍：

| 触发 | 为什么 |
|---|---|
| 改 `apps/app/src-tauri/capabilities/` | 能力边界写错＝开了不该开的权限 |
| 改更新器（updater）配置或签名流程 | 发错包会覆盖用户安装 |
| 新增/升级依赖 | 许可与供应链风险 |
| 改许可、声明、`COPYING.md` | 法律文本 |
| 改构建脚本、CI、打包配置 | 坏了发不出包 |
| 动账户认证相关代码 | 凭据泄露不可逆 |

### 6.5 自审检查表（10 条，逐条打勾）

- [ ] 改动只落在该落的包/目录，没波及无关文件
- [ ] 没有未使用的 import / 变量 / 样式
- [ ] 新增文案走 i18n（若该处已有 i18n 结构），没有硬编码中文
- [ ] 界面改动在 900px / 1280px / 最大化 三档都看过
- [ ] 深浅主题都看过（若改动涉及颜色）
- [ ] `prefers-reduced-motion` 下不出现异常动效
- [ ] 出错路径有提示，不是静默失败
- [ ] 没有把调试输出、console.log、临时代码带进去
- [ ] 提交信息符合 §3，一个提交只做一件事
- [ ] 没动 `pnpm-lock.yaml`（除确实改了依赖）

## 7. 资源预算与验收口径

目标是「低占用」，但必须可测，否则就是感觉。

### 7.1 测量口径

| 指标 | 怎么取 | 注意 |
|---|---|---|
| 常驻内存 | 任务管理器「内存」列（私有工作集） | 不是「提交大小」 |
| 冷启动到窗口可见 | 手动计时 3 次取中位数 | 清空缓存后测 |
| 空闲 CPU | 资源监视器观察 10 秒均值 | 必须在前台、停在首页 |
| 包体积 | `dist/` 与最终二进制大小 | 与上一版比 |

### 7.2 判「有效」的标准

- 内存：**差值必须大于跨启动本身波动（约 500 MB 量级）**，否则记为「测不出」
- 体积：前端 gzip 后变化 ≥ 20 KB 才算一次有效优化
- 启动耗时：3 次中位数差 ≥ 150 ms 才算有效

低于上述阈值的改动可以合，但**不许在 CHANGELOG 里宣称「优化了性能」**。

### 7.3 预算（待标定）

初次安装后测一轮基线，把数值填进下表，之后每次发版对照：

| 项 | 基线 | 上限 |
|---|---|---|
| 常驻内存（空闲） | 待标定 | 待标定 |
| 冷启动到窗口 | 待标定 | 待标定 |
| 二进制体积 | 待标定 | 待标定 |
